# 20261115 — A seeded template is upgraded in place only while its text is exactly a shipped one, and that decision is taken once per row under the entity lock

**Date:** 2026-11-15  
**Status:** Accepted — the architect's decision under the owner's delegation of 2026-11-15 (specs/20261115-crm-offer-wizard, § Amendment (2026-11-15, owner), DD-59 and DD-60; AC-12.5, AC-12.6, AC-12.11; open item O8 kept by the owner's delegated decision, decisions.md § Plan amendment (US-11, US-12), marked OWNER REVIEW); pending the owner's review.

## Context

The first wizard release seeded seven templates per entity under keys `welld-ch-it-v1:<code>`, with "WellD Sagl" written into their texts. The amendment of 2026-11-15 makes the issuer's legal name and address come from the entity profile (US-12): the seeds now bind them through system fields (`[EMITTENTE]`, `[INDIRIZZO_EMITTENTE]`), and the owner asked that rows already seeded be upgraded without anyone recreating or editing them (AC-12.5). Seeding is lazy: `seedWizardTemplates` runs on the first wizard listing of an entity, inside that entity's template advisory lock, and finds each seed by its key. People can edit a seeded row, duplicate it, archive it, or create a template under a seed's name. The wizard is not on `main`, so no production database holds v1 seeds; the owner's dev database does, and it was upgraded by T63. (O8: if no shared environment ever held v1 rows, the owner may drop AC-12.5, 12.6 and 12.11 and this path with them.)

## Decision

We will upgrade a seeded row in place, exactly once, inside the transaction that already holds the entity's template lock and before any seed is inserted. `upgradeWizardSeeds(tx, entity)` (`crm-api/src/offer-templates/wizardSeeds/upgrade.ts`) locks the rows whose seed key is a first-set key (`SELECT … FOR UPDATE`) and decides each one:

- if the stored `source` hashes (SHA-256 of the exact text, with no normalisation) to a recorded shipped first-set revision of that seed's code, the row takes the v2 text and the v2 key, its `version` is incremented, and the write is guarded by `WHERE version = <seen>`, attributed to `system:crm-api`;
- otherwise the row's key moves to the kept key (`welld-ch-it-v1-kept:<code>`) and nothing else changes: no version bump, timestamps kept. A kept row is never looked at again;
- if the code already has a row under its v2 or kept key (amended 2026-11-15, security L-7: a rollback to the first release inserts first-set rows beside the v2 ones, and a roll forward then meets both), the row can take neither key, because the unique index on `(entity, seedKey)` would refuse it and every wizard listing would answer 500. It is decided once the same way: its seed key becomes `null`, and nothing else changes (text, version, state, timestamps). It is then a plain template that no later run selects, and the code is not inserted again because its other row already carries a key.

`name`, `description`, `uses`, `archivedAt` and `language` are never touched. Nothing is created, archived, restored or deleted, and no supersession runs. Only after this step does the insert step run, and it inserts a code only when no row carries any of its three keys (first-set, v2 or kept), so a fresh database receives v2 directly. The recorded revisions live in `crm-api/src/offer-templates/wizardSeeds/v1Digests.ts` as `V1_DIGESTS`: the SHA-256 of every revision of each seed file's text in git history from its first export, each with the commit that first exported it (T1 2, T2 2, T3 1, T4 3, T5 1, T6 1, T1+T3 1). The file is generated by `crm-api/scripts/seed-digests.ts` and checked by `--check`; it is never edited by hand. Each row decided writes one log line with entity, code and outcome, never the text.

## Failure shape

**A system that updates a copy it once wrote decides from the copy's content whether that copy is still its own, and "equal to something we once shipped" cannot tell an untouched copy from one a person chose to leave the same. An update that re-runs on every read then treats each later edit as one more version to replace.** The mistake is a default that overwrites what a person did, because its author confused "the text we wrote" with "the text that is still ours". The same comparison fires in the other direction too: a person's text that happens to equal an old shipped text is replaced as if it were not theirs.

The same shape appears in its mirror-image positions:

- **Writer of a default and reader of the list.** The seed writes when a list is read. A seed that rewrites on read, outside the lock, makes the reader see a change they did not ask for; the reader is the person who owns the template.
- **Update and insert.** Inserting the new version under a new key creates a second template beside the one a person owns: a name clash, a duplicate in the picker, a row the person did not ask for. This is the same mistake in the other direction, and it is the one that is easiest to take for a safe choice.
- **Once and every time.** A rule re-checked on each run turns a one-time decision into a standing override. A kept row that a later edit happens to return to an old text would be replaced, which the owner's rule forbids.
- **Default in code and default in data.** A default shipped inside a migration is applied once and then forgotten; the same default in code is applied on every listing. Either way, the decision about a row must belong to the row, taken where the row is written.
- **Exact and fuzzy.** A comparison that ignores spacing or case overwrites an edit that changed only spacing. The copy is either the shipped copy or it is not.

Recognise it anywhere by: an `UPDATE` whose `WHERE` says "still equal to a text we once stored"; a comparison with normalisation before it decides ownership; a default that is loaded on every listing or start and writes into rows it did not create; a "reset to default" action that does not check for edits; a new seeded key that inserts a row beside one a person owns; a status that is re-derived from text on each read and then written back.

## Options considered

### Option A — exact SHA-256 match against recorded shipped revisions, once per row, under the entity lock and a version guard (chosen)

**Pros:**
- The decision for each row is taken once, in the transaction that writes it
- Idempotent under concurrency: the lock and the `WHERE version = seen` guard make a lost race leave the row for the next read; a test runs five concurrent listings and sees one upgrade (mutation-checked, T63)
- A person's edit, a duplicate (no seed key) and a name-taken seed are never selected
- Drafts from an upgraded template get the AC-8.4 notice through the ordinary version comparison

**Cons:**
- The digest list is a historical fact that must be kept: each shipped first-set revision is recorded before its seed file changes again, and `--check` fails when it drifts
- Kept rows still say "WellD Sagl" until a person edits them

### Option B — new keys insert new rows beside the old ones (rejected)

**Cons:**
- Creates templates the owner did not ask for, next to the seeded names; a name clash skips the new seed, so the upgrade would not even land
- Two copies in the picker, and the v1 rows keep the old text

### Option C — the seed text in a migration (rejected; DD-10)

**Cons:**
- Applied once per database and never again; the text lives in the database, not beside the seed code that reviewers read

### Option D — upgrade every v1 row regardless of its text (rejected)

**Cons:**
- Overwrites what people wrote; AC-12.6 forbids it

### Option E — compare a normalised text (trimmed, whitespace collapsed, case folded) (rejected)

**Cons:**
- An edit that differs only in spacing is overwritten, so the comparison is not about what the person wrote

### Option F — keep the v1 key on edited rows and re-check them on every listing (rejected)

**Cons:**
- A later edit back to the v1 text would be upgraded, which AC-12.6 forbids: the update takes effect once

### Option G — keep the full v1 texts as fixtures (rejected)

**Cons:**
- About 140 KB of look-alike seed text in the repository, when a digest decides the same question

## Consequences

**Positive:**
- Every row is decided once, under the lock, by its own text; the owner's dev database was upgraded by this rule (T63): untouched rows took the v2 text, edited rows kept their text under the kept key
- A person's edit is never replaced by the seed; a duplicate and a name-taken seed are not touched
- An upgraded template's drafts get the existing "template changed" notice (AC-8.4) through the version bump, not a new mechanism

**Negative / trade-offs:**
- The digest list grows with every change to a seed file, and the rule that each shipped revision is recorded before the file changes again is a human rule that `--check` only partly enforces
- Kept rows show the v1 text until a person edits them; the editor's "supplied by the CRM" list (AC-12.1) applies to v2 texts only
- The upgrade path stays in the code until it is removed; it does nothing in a database without v1 rows

- A first-set row that coexists with a decided row of the same code is released (seed key `null`), not upgraded and not deleted: the person's data is kept and the listing never fails on it. Each target key is checked free, under the entity lock, before the write, so the loop cannot hit the unique index.

**Risks:**
- **A row a person edits back to exactly a shipped revision is upgraded once.** Accepted: its text is by then identical to a text we shipped, and the upgrade is announced to any draft through the notice. Mitigation: the exact match, with no normalisation, so the case is as narrow as it can be.
- **A second shared database that holds v1 rows receives the same outcome on its first wizard listing after the release.** Mitigation: the owner's checklist (decisions.md T63) lists the outcome; the log line records each row's outcome.
- **The upgrade path outlives its need.** Mitigation: once every shared environment has run it, a later change may remove the path and the digests together, as the owner decides (O8).

## Compliance notes

- GDPR / data-protection impact: none. Templates are business content; the upgrade writes no personal data, and the log line carries entity, code and outcome only.
- Data residency: compliant with the EU region. It runs in the CRM's own database.
- Audit trail: not required by this decision. Each upgraded row keeps its `version` increment and `updatedBy` = `system:crm-api`, as every template write does.

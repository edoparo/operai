# specs/017 — decisions taken autonomously

The product owner asked for the CRM to be built without them at the keyboard and for every
decision to be documented. Each entry: what was decided, why, and what was rejected. The
architecturally significant ones are also ADR-0052 / ADR-0053.

| # | Decision | Why | Rejected |
|---|---|---|---|
| D-1 | **A new tool, `crm`, as its own service pair**: `crm-api` (Bun + Hono + Prisma, port 8084, logical DB `crm`) and `crm-ui` (federated remote, port 5179), mounted by the shell at `/crm`. | The suite's established shape for a tool that owns data (ADR-0003/0005/0006, inventory precedent). Keeps commercial data in its own database. | Adding CRM tables to `estimai-api` (different domain, would couple deploys); a module inside the shell (ADR-0009: no tool logic in the shell). |
| D-2 | **Four aggregates**: company, contact, deal, activity (tasks are activities of type `task`). | The smallest model that covers "who, what opportunity, what happened, what next". A separate task table would duplicate company/contact/deal links. | Separate `task` table; a generic "entity" table with types; leads as a separate aggregate (a lead is a deal in stage `lead`). |
| D-3 | **Authorization**: catalog app `crm` with `crm:access` (read everything, create/edit companies, contacts, activities), `deal:manage` (entity-scoped, ADR-0015) and `contact:erase` (unconditioned). | Reading the relationship is useful to every consultant; moving money figures (deals) is a sales responsibility and is per entity, like refund and inventory; erasing personal data is a privileged, rare act. | One capability for everything (no separation for deal figures); per-record ACLs (ADR-0036 is for owner-shared documents, not a team CRM); entity-scoping reads (consultants of both entities work for the same clients). |
| D-4 | **Seed**: `admin` gets all three unconditioned; new system role `sales` gets `crm:access` + entity-scoped `deal:manage`; `employee` nothing. | Mirrors `inventory-manager` (specs/015). Access stays admin-assigned (specs/004 product decision). | Granting `crm:access` to every employee by default. |
| D-5 | **Denials**: capability absent → 403; a deal outside the caller's `deal:manage` scope → **403 `out_of_scope`**, not 404; an unknown id → 404. | Every CRM user can READ every deal, so the record's existence is not secret; a 404 would lie. This is ADR-0037's "relationship exists, level insufficient" branch. | ADR-0014's 404-for-out-of-scope (correct only when the record is not readable). |
| D-6 | **The user directory gate is widened to `deal:manage`** (owner/assignee picker). | ADR-0047 names "a second consuming app" as its escalation trigger and requires the addition to be deliberate: done in ADR-0053, gated on a capability whose holders assign owners. | Opening the directory to every `crm:access` holder (too wide for a list of people); no picker at all (owners could never be reassigned). Users without the capability can still assign a task to themselves, the default. |
| D-7 | **Optimistic concurrency** on company, contact and deal writes: integer `version`, `ETag`, required `If-Match`, 428 / 409 `version_conflict`. | Shared records edited by several people; ADR-0038 is the suite's posture. | Last-write-wins; `updatedAt` as precondition (rejected by ADR-0038). Activities are exempt: only their author edits them. |
| D-8 | **Fixed stage probabilities** (10/25/50/75/100/0) in code, returned by `GET /pipeline` so the UI never duplicates them. | Configurable probabilities are a settings store of their own (ADR-0027 shape) for a number nobody has asked to tune yet. Open question O1. | A settings table now. |
| D-9 | **Money**: integer minor units, `CHF` or `EUR`; weighted amount = `roundHalfUp(amount × p / 100)`, computed once per deal then summed; totals per currency, never converted. | ADR-0025: round once, one rule; the two entities bill in different currencies and no FX rate exists in the suite. | Floats; a single converted total. |
| D-10 | **"This year" for won/lost** = `closedAt` in the current calendar year, UTC. | Simple, matches how the partners talk about the year; fiscal year = calendar year as in specs/015. | Rolling 90 days; a configurable period. |
| D-11 | **Company names unique case-insensitively, archived included** (functional unique index on `lower(name)`), 409 `company_name_taken` with the existing id. | Duplicates are the classic CRM rot; including archived ones means a returning client is unarchived rather than recreated. | Fuzzy duplicate detection (later, non-goal); uniqueness on active companies only. |
| D-12 | **Archive instead of delete** for companies and contacts; no hard delete of companies or deals at all. | History matters more than tidiness; nothing in v1 requires deletion of a company (not personal data). | Soft-delete with a `deletedAt` that hides everywhere. |
| D-13 | **Contact erasure** is a hard delete; activities keep their row with `contactId` set to NULL (FK `ON DELETE SET NULL`). Free-text bodies are NOT scrubbed. | GDPR art. 17 for third-party personal data. Scrubbing free text cannot be done reliably by code; the confirm dialog tells the eraser to edit activity text that names the person. | Anonymising in place (keeps a row that is still personal data); refusing erasure while activities exist. |
| D-14 | **No notifications in v1.** | Pushing via notify-api needs a new `SERVICE_CLIENTS` entry, secrets in 1Password, env-doctor wiring and an infra rollout that cannot be done unattended. The seam is obvious (task assignee ≠ author) and is the first follow-up. | Implementing the client unwired (dead code), or forwarding the user JWT (rejected by ADR-0044). |
| D-15 | **People are stored as opaque auth user ids** and names resolved live through `auth POST /authz/users/identities`, failing soft (ADR-0039). A write that sets an owner/assignee checks that the id is an **active** user and fails **closed** (503) when `auth` cannot answer. | A display name is decoration, but assigning a record to a non-existent or deleted user would corrupt it. | Denormalising names; trusting the client's id unchecked. |
| D-16 | **Paging**: offset pagination with `total` on every list (`page`, `pageSize` ≤ 100; the pipeline board asks for open deals with `pageSize` ≤ 200). | Every CRM list grows with the organisation (design-system § Paging). Offset + total fits `Pagination`. | Cursor paging (no total for the UI's "Page 2 of 5"). |
| D-17 | **Search** is a case-insensitive substring (`ILIKE`) on the listed fields. | Enough at wellD's size; no new Postgres extension (ADR-0041 avoided `pg_trgm` too). | Full-text search. |
| D-18 | **Audit**: no separate change log; `createdBy`/`updatedBy` on rows plus the activity timeline. | CRM records are not financial or governance records, so ADR-0033's Tier 1 does not apply; Tier 2 would be a new table with no reader yet. | An append-only event table now. |
| D-19 | **Activity edits by author only; tasks completable by anyone with access.** | A note is someone's account of a conversation; completing a follow-up is teamwork. | Free edits for all. |
| D-20 | **Superseded by D-25 (2026-11-01).** **Pipeline board without drag and drop**: one card per open stage, each deal a link; moving happens on the deal page through a "Move to stage" dialog. | Keyboard- and screen-reader-accessible by construction; the design system has no DnD board and adding one is a library change with its own a11y design. | `@dnd-kit` board (EstimAI uses it only in an editing grid, a documented exception). |
| D-21 | **Rigor `mvp`**, tests: authorization matrix, domain rules (stages, money, uniqueness, concurrency, scoping) against a real Postgres, UI copy parity and no-hardcoded-strings scans, key component tests. No shell e2e journey yet. | The e2e harness needs the full stack plus seeded sessions; adding a journey is the next step before production rigor. | Shipping without the domain tests. |
| D-23 | **`crm-api/.envrc` and `crm-api/.env.example` are committed, like the other backends.** The `.envrc` loads the root `.envrc` (`source_up_if_exists`), builds `DATABASE_URL` from the root `POSTGRES_*` values and loads `.env`. It has no `op read`, because crm-api has no secret. `.env.example` holds the other, non-secret local values. *Revised 2026-11-01:* the first version of this entry said `.envrc` was gitignored and left it to the developer. That premise was wrong (`.envrc` is tracked for every backend), and `mise run dev` failed to start crm-api. The agent's secret-file guard still stops the agent from writing these files, so the developer copied them in from a draft. | Same shape as inventory-api, so `mise run dev`, `db:migrate` and `env:doctor --env local` work with no extra step. The password stays in the root `.envrc`, never in this file. | Leaving the files to the developer (it broke the first `mise run dev`); hard-coding credentials in `mise.toml`. |
| D-24 | **OWASP review follow-ups (2026-11-01).** Fixed:<br>(a) an owner or assignee id starting with `system:` is rejected (422 `owner_not_active`), because a system principal may author a record but never own one;<br>(b) `page` is capped at 100 000 (422, not a Postgres OFFSET 500);<br>(c) crm-ui renders the company website as a link only if it is `http(s)`, as defence in depth behind crm-api's check;<br>(d) a comment beside the directory gate says no catalog may reuse `deal:manage`.<br>Not fixed:<br>(e) seroval and better-auth advisories: seroval reaches the browser through `@tanstack/react-router`, and better-auth's vitest/undici/tinypool advisories come through test tooling that never reaches the bundle. Both libraries are Module Federation singletons, so the copy the user's browser runs is the shell's (seroval 1.5.5). Only crm-ui's lockfile was refreshed (seroval 1.7.6).<br>(f) zod 3 advisory in crm-api: limited by the 64 KiB body limit.<br>(g) no rate limiting in crm-api, as in the other resource servers.<br>(h) contact erasure has no persistent audit entry. | (e) Bumping one remote's singleton range above the shell's would load two routers; the fix is a suite-wide bump of router and better-auth in every frontend, together.<br>(f) zod 4 means `@hono/zod-openapi` 1.x for every backend.<br>(g) Its own decision for the suite.<br>(h) Its own decision. These belong in separate `chore` branches, not in the CRM feature. | Raising only crm-ui's ranges (version skew under the singleton); upgrading zod only in crm-api (the backends would diverge). |
| D-25 | **Drag-and-drop pipeline board** (2026-11-01, at the product owner's request; supersedes D-20).<br>- Six columns: the four open stages plus Won and Lost, which hold this year's closed deals (`GET /deals?board=true`, the set `GET /pipeline` totals; D-10).<br>- Jira/GitLab shape: compact lanes and cards; the pipeline page uses the `wide` layout so the six lanes fit without scrolling (the board scrolls by itself only on a narrow screen).<br>- **The whole card is the drag source** (revised after the first try, where a grip handle and a scrolling board were rejected by the owner). Pointer: an 8 px threshold before a drag starts, so a click opens the deal. Keyboard: a card is one tab stop; Space picks up, left/right arrows jump a whole lane, Space drops, Escape cancels, Enter opens the deal. Each step is announced in the user's language.<br>- A drop on Lost opens the "Move to stage" dialog preset to Lost for the optional reason; any other drop moves at once.<br>- The move sends the deal's `version` as If-Match, so `DealSummary` now carries `version`. A stale move shows the reload banner.<br>- The deal is drawn in its new column at once and the board reloads for the server's figures.<br>- Only deals in the caller's `deal:manage` scope are draggable; the others are plain link cards.<br>- The "Move to stage" dialog on the deal page stays. | The owner asked for it, and dnd-kit gives the keyboard and screen-reader path D-20 was protecting: the card is a focusable `role=button` with drag instructions, and the moves are announced. A column-jumping keyboard coordinate getter makes six presses enough to reach any stage. `@dnd-kit/core` is already the suite's DnD library (estimai-ui). The board stays in crm-ui: it is the only board in the suite. A second app needing one moves it into `@operai/ui` (AGENTS.md). | A grip handle beside each card (tried first: unlike the boards people know); a horizontally scrolling board in the default width; a separate "closed" table beside the board (no drop target for Won/Lost); a new library component before a second consumer exists. |
| D-26 | **Task filter: me, everyone, or one colleague** (2026-11-01).<br>- `GET /tasks?assignee=` accepts `me`, `any` or a user id.<br>- The colleagues offered come from a new `GET /tasks/assignees` (everyone tasks were ever assigned to, names resolved live), not from auth's user directory.<br>- The tab is renamed "Tasks" ("Attività da fare" in Italian).<br>- **Who may assign whom, unchanged:**<br>&nbsp;&nbsp;- any `crm:access` holder creates tasks;<br>&nbsp;&nbsp;- the server accepts any **active** Operai user as assignee (D-15), even one without `crm:access`;<br>&nbsp;&nbsp;- the UI picker, which needs auth's directory (ADR-0053), is open only to `deal:manage` holders, so everyone else assigns to themselves. | Every `crm:access` holder can already read every task with its assignee (`assignee=any`), so the assignee list is a projection they could rebuild by hand. ADR-0042's reconstructibility test applies: no new permission, and the directory stays narrow. | The user directory as the colleague list (would need ADR-0053 widened to `crm:access`); a free-text name search. Limiting assignees to CRM users is open question O4. |
| D-22 | **Infrastructure not provisioned.** Railway service, Vercel project, DNS and secrets are NOT created from this session; the code, `railway.json`, `vercel.json`, CSP and env-doctor manifest are ready for `provision-tool`. | Outward-facing, hard-to-reverse actions on shared infrastructure need the owner present. | Provisioning unattended. |

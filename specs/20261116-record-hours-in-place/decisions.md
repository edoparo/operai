## T8 · frontend-dev · 2026-11-17
- scope: `WeekRowPreset` is declared locally in `weekGrid.ts`, member for member as plan § `EntryDialog` writes `EntryPreset['on']`, importing the choice types (`ProjectChoice`, `DealChoice`, `MeetingChoice`) from `searchers.ts` as `import type`. `EntryDialogModel.ts` is untouched. — why: T1 owns `EntryPreset`, and T8 must not edit that file. After integration `WeekRow['preset']` can be swapped to `EntryPreset['on'] | null` with no behaviour change. — where: `hours-ui/src/lib/weekGrid.ts`
- reinterpretation: `weekDays`, `shiftWeek` and `weekGrid` throw a `TypeError` when the `monday` argument is not a real Monday, and `mondayOf` throws on a non-day, as `presetRange` does. The plan did not say what happens to a non-Monday. — why: a caller that passes today's date instead of its Monday gets a loud error, not a silently shifted week. — where: `week.ts`, `weekGrid.ts`
- reinterpretation: `readWeekParam` returns this week, not the named week, when the named day's week starts before `MIN_DAY` (2000-01-01) or ends after year 9999. A `week` outside that range is treated like garbage. — why: the plan says "any real day → its Monday", but such weeks would only produce a 400 from hours-api or an unwritable date. This follows the `HoursFiltersState` rule that a pasted link never reaches the API as a refused request. — where: `week.ts`. `shiftWeek` applies no floor: it only throws a `RangeError` outside years 100 to 9999, so Previous at the floor ends in an API error with Retry.
- assumption: `shiftWeek(monday, weeks)` takes any whole number of weeks (the plan says ±1) and throws on a fraction or NaN. — why: it makes jump-by-N possible at no extra cost. — where: `week.ts`
- assumption: when entries of one row disagree about visibility, because a source answered on one page of the walk and not on the next, the row is `hidden` if any entry says hidden. Otherwise it is named by the first entry that is visible with a label, and otherwise `unavailable`. — why: a name the server withheld must never be shown, and the order of entries must not change the row. — where: `weekGrid.ts` `summaryOf`
- assumption: a visible entry that arrived with a null label gives `name: null` and `visibility: 'unavailable'`, which is how `rowName` reads it. This keeps the invariant that `name === null` means the visibility is not `visible`, so T9 can render the row from `name` and `visibility` alone. — where: `weekGrid.ts`
- assumption: an own entry whose target id is null goes to the one `<kind>:unknown` row, with no name and no preset, and its visibility is `hidden` or `unavailable`, never `visible`. A real id literally equal to `unknown` would collide with that key; judged unrealistic for cuids and UUIDs. — where: `weekGrid.ts`
- assumption: a category row's `retired` is true when any of its entries says so, and its `name` is the first entry's category name. A retired row keeps its name and hours, with `preset: null`. — where: `weekGrid.ts`
- assumption: rows are sorted with `Intl.Collator(document.documentElement.lang, { sensitivity: 'base' })`, read when `weekGrid` runs (so `weekGrid` keeps its two-argument signature). It falls back to the platform default if `document` is missing, `lang` is empty or the tag is invalid, and ties break on the row key by code-unit order. — why: the order is then the same whatever order the server sent. — where: `weekGrid.ts`
- assumption: `weekGrid` throws a `RangeError` naming the entry id and day, never the note, for an entry whose day is not one of the week's seven days. The check is set membership, so `2026-11-1` or an empty day also throws. — where: `weekGrid.ts`
- scope: day arithmetic helpers (`dayOf`, `isoOf`, an add-days step) are duplicated privately in `week.ts`, a few lines, because `period.ts` does not export them and is not in T8's `touch:` list. — where: `week.ts`

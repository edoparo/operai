# Security review: CRM offer wizard (OWASP Top 10)

Branch `feat/crm-offer-wizard` vs `main`. Static review plus one pure-function probe of the engine
(no database, no service). Reviewer: owasp-reviewer, 2026-11-15.

## Verdict: FAIL (1 medium defect)

0 critical, 0 high, 1 medium, 2 low, 3 info.

## Findings

### [M-1, MEDIUM] A04/A05 (resource exhaustion): no bound on the resolved text, so a template multiplies an answer
- Where: `crm-api/src/offers/engine/resolve.ts` (no cap on a resolved section, opening, cell or list; the 20 000-character limit exists only for hand edits, lines 959-960), reached from `crm-api/src/offer-drafts/offerDrafts.routes.ts:675` (generate runs `resolveOffer` twice and then renders the PDF), the browser preview (the same engine in `crm-ui/src/lib/offerEngine/resolve.ts`) and `contractPdf.ts`.
- Scenario: a user with `deal:manage` on the entity saves a wizard template that passes `template_invalid` (150 000 characters allowed). One line holds `[DESC]` repeated about 50 000 times. A draft then holds a 20 000-character answer for `DESC` (allowed by `answersSchema.ts`, inside the 512 KiB body). Probe on the shared engine: 100 references gave a 2.0 MB section body in 42 ms, and 400 gave 8.0 MB in 190 ms, with zero template errors. The growth is linear, so the maximum template reaches about 1 GB of string for one section. Any colleague who opens the Preview step freezes their tab. Generate in the single crm-api process (single thread, deploy shape of other Bun services) allocates the string twice, then lays it out in pdf-lib. That is an out-of-memory or event-loop stall that blocks every CRM user. The template author and the victim can be different people, since templates are shared per entity. The plan (§ Security, "Resource exhaustion") and DD-3 promise a 20 000-character section body bound. It is enforced on the template source and on hand edits, not on the output.
- Fix: bound the OUTPUT in the resolver (byte-identical copy in both apps, same vectors).
  - Count the printed characters while resolving and stop once a section body exceeds `MAX_EDIT_BODY` (or a total of about 500 000).
  - Report `section_too_long` / `offer_too_large` as an `invalid` issue, so generate answers 422 `offer_incomplete` and the preview shows the problem list.
  - Check the substitution while the buffer is built (`escapeValue` call sites), not afterwards, so the allocation never happens.
  - Optionally, in `assertTemplateValid`, reject a template whose number of field references times the field cap can exceed the budget.
  - Add a test with the 50 000-reference template.

### [L-1, LOW] A03/A09: NUL characters in answers are not refused, so a save is a 500 and the raw error is logged
- Where: `crm-api/src/offer-drafts/answersSchema.ts` (strings and record keys have no NUL check), `answers.ts:543,572` (`RESERVED` covers U+E000-U+E0FF and the token brackets, not U+0000), `offerDrafts.routes.ts:534` (`updateMany` with the JSONB), `index.ts:115` (`console.error("[uncaught]", err)`).
- Scenario: the draft is JSONB and Postgres rejects `\u0000` in jsonb. A body with `"fields":{"A":"x\u0000"}` passes `PutDraftSchema` and `checkAnswers`, then fails at the database as an unhandled error: 500, not 422 `answers_invalid`. The template route already refuses NUL (`noNul`). The raw Prisma error is logged. Depending on the driver-adapter message format it can carry the statement parameters (the draft's answers: prices, client data). It is also a one-request way to make the autosave loop show an unexplained failure.
- Fix: add `.refine((s) => !s.includes("\u0000"))` to `text`, `key`, hand edit and list strings (or add U+0000 to the `RESERVED` set in `answers.ts` so `checkAnswers` returns `reserved_character` with a path, in both copies). Optionally log only `err.name`/`code` for Prisma errors in `onError`.

### [L-2, LOW] A01/A04: a read-only call changes template state, and for any entity
- Where: `crm-api/src/offer-templates/offerTemplates.routes.ts:424-426` (`GET /offer-templates?entity=welld_ch&formats=wizard` calls `seedWizardTemplates`, which archives the Italian legacy templates through `supersedeLegacy`).
- Scenario: the route needs only `deal:financials` and no entity scope. A welld_it-only reader (or anyone who loads the wizard's template step first) flips welld_ch's classic templates to archived. Seeding is by design (DD-10) and idempotent, but archival is a write with `version` bumps and `updatedBy = system:crm-api` by a GET for a caller who could not write a welld_ch template. A restore is refused while a wizard template is active (`template_superseded`), so it is one-way.
- Fix: leave as designed if the owner accepts it (the plan records lazy seeding as intentional), or require `assertInScope(dealScope(c), entity)` before seeding. Record the decision in `decisions.md`.

### Info
- I-1 (A09): a 422 `answers_invalid` built from a zod issue (`putHook`, `offerDrafts.routes.ts`) uses `issue.message`, which for enum members (`lastStep`, `kind`) can echo the received value. It is the caller's own input and not logged, so no leak. If you want the "no value in any error body" rule to hold literally, send the code only (`reason: "shape"`).
- I-2 (A04): generate (PDF render, up to 20 MiB of attachment reads, an estimai call, a lock on the deal) has no per-user rate limit. The same holds for the existing 018 route, so it is not a regression. The 30 s transaction budget and the deal lock bound it.
- I-3 (A09): draft autosave parses the template (up to 150 000 characters) on every PUT. It is linear and fuzz-tested, so it is not exploitable beyond M-1, but it is the hot path if the template grows.

## Checked and found sound
- Authorization (A01): every draft route (`context`, `GET`/`POST`/`PUT`/`DELETE` draft, `summary`, `template`, `generate`) uses `generating` (`deal:financials` + `deal:manage`), then `loadDealInScope` (404 deal, 403 `out_of_scope`) runs BEFORE any draft read. A foreign-entity caller gets the same answer with or without a draft (AC-6.2). The summary never selects `answers`. `{ draft: null }` appears only after the gate. Template ids from another entity are 404 (`loadWizardTemplate`, generate `template.entity !== deal.entity`). The target offer must belong to the deal and be undeleted, and the PUT target cannot change (`target_changed`). Attachment ids are re-checked against `dealId` and `status=stored` at generate (`loadAttachments`), and contact ids against the company's contacts. A draft's FK to `deal` cascades, and a template cannot be deleted under it (RESTRICT).
- Integrity: `If-None-Match: *` on create (the primary key arbitrates, P2002 handled), `If-Match` CAS on PUT, DELETE, template switch and generate (`updateMany where version`), a version-conditioned draft delete inside the generating transaction, edit CAS on the offer version with `sentAt: null`, and compensation (object deleted on any failure, the replaced PDF deleted only after commit). Template supersession runs under one `pg_advisory_xact_lock` per entity with a re-read under the lock.
- Mass assignment: every draft body schema is `.strict()` (unknown members refused, `__proto__` refused as a key). Generate has no body, so the document is what is stored. The wizard template body is `.strict()` and the format cannot be set by the client.
- Injection (A03): `compute` is a hand-written recursive-descent parser (200 characters, depth 16, BigInt arithmetic, no `eval`/`Function`). Answers are escaped before entering markup (`escapeValue`: `\ [ * _ | {`, line-start markers, per line kind). Reserved characters (U+E000-U+E0FF, the hand-edit brackets and the reference brackets) are refused in templates and answers. The reference token is filled server-side only. `printable` maps everything outside WinAnsi to "?" before the PDF. Inline parsing memoises the `::` search (linear).
- `template_invalid` carries line, code, severity and the declared identifier name only, never text. `offer_incomplete` carries names and template labels only. The only log line on the draft routes records ids and versions, never answers.
- DoS bounds that hold: 512 KiB body (413 `draft_too_large`, applied by path regex before routing), answer caps (400 entries, 20 000 characters, 50 x 2 000 lists, 50 rows, 10 extra cost lines, 200 hand edits), template 150 000 characters with nesting 8, and `no-store` on context, draft and summary.
- Migration `20261115120000_offer_wizard`: additive, no data change, no archival. The FKs are `RESTRICT` on templates and offers and `CASCADE` on the deal. CHECK constraints tie format to content and target to offer. No injection surface.
- crm-ui: no `dangerouslySetInnerHTML`, no browser storage (a `noBrowserStorage` test exists), no `keepalive`/`sendBeacon`, ids passed through `encodeURIComponent`, template problems and values rendered as React text, and the `window.open` calls use `noopener`.

## Defect list (>= medium)
1. M-1: bound the resolved output (engine, both copies) and add a test with the amplifying template.

### M-2, MEDIUM, A04/A05 (resource exhaustion): the recursive NUL scan in `parseBody` is quadratic in nesting depth and overflows the stack
- Where: `crm-api/src/offer-templates/offerTemplates.routes.ts` `pathOfNul` (about line 214) called by `parseBody` (about line 236), reached from `PUT /offer-templates/{id}` (lines 583 and 592, inside the `casUpdate` transaction callback).
- Scenario: the body schema of that route is `z.object({}).passthrough()`, so the 1 MiB document cap (`index.ts` `isDocumentWrite`) is the only bound and nesting is unbounded. A caller with `deal:financials` + `deal:manage` sends `[`x500 000 then `]`x500 000 (about 1 MB, 100 KB is enough). `JSON.parse` accepts it; `pathOfNul` recurses once per level and copies the whole path array on every level (`[...path, index]`), so the work is O(depth squared). Probe (verbatim copy of the function): depth 5 000 = 31 ms, 20 000 = 340 ms, 40 000+ = `RangeError: Maximum call stack size exceeded` after about 1 s of CPU. Each request therefore blocks crm-api's single event loop for about 1 s while a database transaction is open, answers 500 and logs the raw error. It is repeatable by one account, and templates are shared per entity. Before D7 the passthrough object was never walked, so this is new in this round.
- Fix (either): (a) drop the generic scan and put the existing `noNul` refine on the string members of the legacy `TemplateContentSchema` (the wizard body already has it), so the schema, which is flat and strict, is the only walker; or (b) make the scan iterative with an explicit stack, a depth cap (the legacy body is a shallow nest, so cap at about 8 and answer 422), no per-level path copy (build the dotted path only when a hit is found). Add a test with a 100 000-deep body that answers 422 in under 100 ms.

### L-4, LOW, A03/A09: `OfferParams` and `AttachmentParams` still take a NUL
- `crm-api/src/offers/offers.routes.ts:81` (`id`, `offerId`) and `crm-api/src/attachments/attachments.routes.ts:33` (`id`, `aid`) are `z.string().min(1).max(64)` without the refine, so `%00` in `offerId` or `aid` reaches a text-column lookup: the same 500 and raw log line D7 closed for `IdParams`. Capability-gated, own request only, no data in the error. Fix: reuse one shared id schema (export the refined string from `lib/http.ts`) in both. The D7 note "`IdParams` is the single root cause" is therefore not literally true.

### I-5, INFO
Correction to my round 2: I wrote that a field in a heading is not resolved. It is (`## [D][D][D]` resolves, and the new vector proves it). The conclusion then drawn (the heading-only path is unreachable) was wrong, and D6 correctly handles it now. No residual issue: the fallback heading is `printable(source.heading)`, bounded by the 150 000-character template, and the whole template holds at most 15 sections.

### M-2: closed (`pathOfNul`, `offerTemplates.routes.ts`)
- Stack safety and linearity: the scan is a loop over an explicit stack, with parent links instead of a copied path; the dotted path is built only on a hit (and is bounded by the depth cap). Probes, each under 20 ms:

  | Shape | Result |
  |---|---|
  | array nested 32 levels | null (accepted) |
  | array nested 33 levels | `too_deep` |
  | array nested 500 000 levels (about the 1 MiB cap) | `too_deep`, 16 ms |
  | object nested 150 000 levels | `too_deep`, 3 ms |
  | array of 500 000 numbers | null, 17 ms |
  | array of 200 000 strings | null, 6 ms |
  | object with 100 000 keys (NUL key last) | hit, 10 ms |
  | 1 MB string, NUL at the end | hit, 0 ms |
  | 100 000 siblings, each 4 levels deep | null, 11 ms |

- Legitimate bodies: a template body is a nest of about four levels (object, sections array, section, string), so 32 cannot refuse a real one.

### M-3, MEDIUM, A06: `pdfjs-dist@5.7.284` is inside the range of GHSA-hq66-cqwq-w95j (CVE-2026-16633, high)
- `crm-ui/package.json:24` (`"pdfjs-dist": "5.7.284"`), `crm-ui/pnpm-lock.yaml`. Repro: `cd crm-ui && pnpm audit --prod` lists `pdfjs-dist`, "PDF.js: Arbitrary JavaScript execution upon opening a malicious PDF", vulnerable `>=5.6.83 <6.2.108`, patched `>=6.2.108` (published 2026-08-06). ### M-5, MEDIUM, A04/A05: `boundPdf` measures a different file than pdf-lib and pdf.js decode
Consequence, measured: a `deal:manage` holder of an entity uploads one PDF and confirms it; `checkLetterhead` answers `ok: true`, the file is stored, and (a) crm-api itself inflates it inside the confirm request, on every later offer generation (`contractPdf.ts:795` `embedPdf`, which decodes the page's `/Contents`), and (b) the browser of everyone who previews an offer of that entity inflates it on the main thread. Decoded size is not capped by the upload limit: a 1 MiB file gave a crm-api process 3.65 GB peak RSS and 3.8 s of blocked event loop (`t6.ts 1024`, header-spelling variant); at the 5 MiB the route accepts that is about 18 GB, an out-of-memory kill of the whole service. Each variant below is accepted although the same bytes without the trick are refused (`decoded_too_large`). One root cause, three spellings: the module predicts, with its own tokenizer and its own filter decoders, what the real readers will decode, and the prediction is wrong wherever the readers are looser than the module.

- **M-5a, object header spelling** (`pdfBounds.ts:538`, `headerRe = /(?<![0-9])(\d{1,10})[ws]+(\d{1,5})[ws]+obj/`). A stream is only found through an `N G obj` header the regex accepts. pdf-lib and pdf.js accept an object number of any length (leading zeros), a generation number of any length (`000000` is generation 0 in an xref table), and a comment between the tokens. Repro (`t1.ts`): a valid one-page A4 PDF whose content object header is `4 000000 obj`, or `00000000004 0 obj`, or `4 %x` newline `0 obj`, holding a 256 MiB-of-spaces Flate bomb (261 KB): `boundPdf` returns `{ok:true, decodedBytes:0, objects:3, streams:1}` (the object is not counted at all), `checkLetterhead` returns `{ok:true}` after pdf-lib inflated it (about 1 s), and pdf.js `getOperatorList` runs 0.9 to 1.0 s at 680 MB RSS, the same as the plain header. The `stream` keyword is counted (`streams:1`) but never decoded because it has no recognised header.
- **M-5b, LZW "future code"** (`pdfBounds.ts:441`, `else break; // a code from the future: the decoder stops`). pdf.js 6.4.299 `LZWStream.readBlock` does not stop on a code at or beyond `nextCode`: it emits the previous sequence plus its first byte, one byte longer each time, and keeps going (pdf-lib's decoder is the same code). A stream of one literal then 3 800 such codes then a clear code, repeated, decodes to about 7.4 MB per 5.2 KB. Repro (`t9.ts 50 lib`): 270 KB PDF, `/Filter /LZWDecode`; `boundPdf` says `decodedBytes:1`; `checkLetterhead` ok in 1.4 s at 1.28 GB peak RSS; pdf.js 1.2 s, 1.0 GB. Linear in the cycles, so 1 000 cycles (about 5 MiB) is about 7.4 GB. The module's first-code rule (`prev < 0 && code > 255` stops) differs from pdf.js in the same way.
- **M-5c, ASCII85 digits outside 33 to 117** (`pdfBounds.ts:335`, `if (c < 33 || c > 117) continue;`). pdf.js `Ascii85Stream` takes every non-whitespace byte as a digit (`c - 0x21`, no range check; `z` only at a group start), pdf-lib the same. A value is written with one digit carried (`d_i - 1`, `d_{i+1} + 85`, a byte 118 to 202); the module skips those bytes, so its groups desynchronise, the next stage (Flate) sees garbage, and the chain counts about nothing. Repro (`t10.ts 256`): `/Filter [/ASCII85Decode /FlateDecode]`, 327 KB PDF decoding to 256 MiB: `boundPdf` `decodedBytes:226377`, `checkLetterhead` ok at 969 MB peak RSS in 1.0 s, pdf.js 935 MB.
- Not affected (compared against 6.4.299): ASCIIHex (same digit rules, same `>`), RunLength (same 128 EOD and repeat counts), Flate (node zlib is stricter than both readers on headers and stored-block lengths, so it cannot undercount), and `BrotliDecode`, which pdf.js 6 ships, is refused as an unknown filter.
- Fix, in order of soundness. (1) Do not re-implement decoders to predict other people's output: allow, for every non-image stream and for the decoder part of an image chain, the single filter `FlateDecode` (a letterhead has no use for LZW, ASCII85, ASCIIHex or RunLength) and refuse the rest as `unbounded_stream`; the Flate path already uses the real inflate and is conservative. If another filter must stay, run it through pdf-lib's own `decodePDFRawStream(...)` and pull at most `cap + 1` bytes with the stream's incremental `getBytes(length)`, so the bound is taken by the code that will run later. (2) Header detection: `(\d+)` without a digit cap on both numbers, comments counted as whitespace (`(?:[\0\t\n\f\r ]|%[^\r\n]*[\r\n])+`), and a cross-check that refuses (`unbounded_stream`) when a `>>` followed by whitespace or comments and `stream` occurs where no parsed header produced a stream. (3) A differential test that is the regression net for the whole class: for random and adversarial inputs, the module's decoded length per filter equals pdf-lib's (and the three PDFs above, by name, as vectors). The existing 23 tests cover well-formed streams and lying `/Length`; none mixes a spelling or a non-canonical encoding.

### M-6, MEDIUM, A04: a 1.6 KB letterhead makes pdf.js spend seconds and gigabytes with no stream to count
`boundPdf` bounds bytes of stream data; the cost of drawing a page is also operators executed, and nothing bounds those. Repro (`t3.ts 4 30`, 1.6 KB, accepted by `boundPdf` and `checkLetterhead`): a page whose content calls Form XObject F1 thirty times, F1 calls F2 thirty times, F2 calls F3, F3 calls F4, which draws one line: pdf.js `getOperatorList` produces 2.49 million operators in 6.6 s at 1.75 GB RSS (`levels 3 fan 40`: 0.56 s, 294 MB; `4 x 20`: 1.4 s, 470 MB). Cost is the product of the fan-outs, so five levels of 30 is about 24 million operators (minutes, then an out-of-memory tab). pdf.js has no guard against a DAG of forms (only against cycles); `renderLetterhead` runs it on the main thread, so the previewer's tab is frozen (the 10 s budget cannot interrupt it, the L-6 point). The same letterhead is embedded into every generated offer PDF (pdf-lib copies the form graph once, so the server is fine) and then opened by the client's own viewer. Tiling patterns with a tiny `XStep`/`YStep`, Type 3 glyph procedures and shadings are the same shape and I did not try them.
- Fix: this cannot be bounded by counting stream bytes. Either (a) bound the expansion at confirm: parse the page's resource graph, count `Do` invocations in the decoded content streams with a DAG product (`calls(form) = 1 + sum of children`), refuse above a figure such as 50 000 (`too_complex`), and refuse patterns and Type 3 fonts outright for a letterhead; or (b) take the parser out of the previewing browser: render the letterhead to a PNG once, at confirm, in a child process with a timeout and a memory limit (or a worker that can be terminated), store the PNG beside the PDF and let the browser draw only the image (the structurally sound answer to "an uploaded file is parsed on every person's main thread"; it reverses the main-thread choice of ADR 20261115-letterhead-preview-pdfjs-main-thread-in-the-remote, so it needs the owner). If neither is wanted now, record this as an accepted residual with the owner's name next to it, as R-numbered items are elsewhere.
